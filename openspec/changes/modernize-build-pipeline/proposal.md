## Why

The Round 1b build modernization audit (`.ntm/swarm/2026-11-02/r1b/r1b-VioletJaguar.md`, cross-reviewed in `.ntm/swarm/2026-11-02/r3/r3-TealBay.md:219-280`) identified four concrete build and CI contract gaps in the live Astro 7.4.5 pipeline (`package.json:89`):

1. **Lighthouse CI spec-vs-generator contradiction:** `openspec/specs/check-site-quality/spec.md:13-20` requires Lighthouse CI to start `scripts/lhci-serve.mjs` and wait for a `READY` line on `http://localhost:8081/` (also claimed in `README.md:210-211,690-691`), whereas `scripts/sync-build-config.mjs:158-173` actually generates `lighthouserc.json:5-15` with `"staticDistDir": ".build/dist"` and `.github/workflows/lighthouse.yml:27-28` runs `npx lhci autorun --config=lighthouserc.json` directly against `@lhci/cli`'s built-in static server (`node_modules/@lhci/cli/src/collect/collect.js:186-222`). Moreover, `scripts/lhci-serve.mjs:24` shells out to `npx http-server`, which is not a declared dependency in `package.json:83-111`.
2. **Undocumented `.astro/` root artifact exception:** `openspec/specs/build-config/spec.md:15-23` and `docs/build-artifacts.md:7,70-71,102` state that all runtime build, cache, and report artifacts live under `.build/` with only `.lighthouseci/` and `.lycheecache` named as CLI-managed exceptions. While `astro.config.ts:14` routes `cacheDir` to `BUILD.cache.astro` (`.build/cache/astro`), `astro@7.4.5` hardcodes `const dotAstroDir = new URL(".astro/", config.root);` in `node_modules/astro/dist/core/config/settings.js:16-17` for generated TypeScript declarations (`.astro/types.d.ts`, `.astro/content.d.ts`), CLI preferences (`.astro/settings.json`), and `astro dev` content-layer storage (`data-store.json` in dev mode; production builds use `settings.config.cacheDir` per `node_modules/astro/dist/content/paths.js:7-9`). `.gitignore:26` ignores `.astro/`, but the spec and artifact docs omit it.
3. **Seven redundant initial lifecycle builds per Playwright CI run:** `.github/workflows/playwright.yml` independently runs `npm ci` and `npm run build` (`astro build` plus all 12 postbuild stages) in each of the 5 `test` matrix shards (`.github/workflows/playwright.yml:80-81,101-102,119-120`), in `visual-regression` (`.github/workflows/playwright.yml:250-254`), and in `accessibility` (`.github/workflows/playwright.yml:384-387`) — 7 initial full builds of the identical commit SHA in every PR and `main` workflow run (distinct from the 4 intentional negative/positive schema-validation builds in `tests/content-collections.spec.ts:43-58,107-203`).
4. **Opaque 12-stage `&&` postbuild string:** `package.json:40` chains 12 postbuild gates in a single `&&` shell command with no per-stage timing visibility and repeated `npm run` wrapper overhead across 8 stages, making regressions in postbuild latency or failure attribution harder to diagnose.

Rationale: font binary sourcing, subsetting, `@font-face` metrics overrides, and visual baseline reseeding already have a dedicated OpenSpec change and postbuild gates (`scripts/verify-font-self-hosting.mjs:1-280`); duplicating them here would create conflicting spec deltas.
- **Removing or weakening any existing postbuild gate:** All 12 stages in `package.json:40` remain mandatory and fail-fast. Rationale: every stage enforces a live security, accessibility, indexation, or design-contract invariant.
- **Cross-workflow or deploy artifact reuse:** `.github/workflows/deploy.yml` and `.github/workflows/lighthouse.yml` continue to run `npm run build` independently in their own workflow runs. Rationale: reusing artifacts generated in untrusted `pull_request` runs for deployment or across decoupled workflows introduces supply-chain and artifact-poisoning risks without a signed attestation framework.
- **Coalescing `sri.mjs` and `csp.mjs` into a single in-memory Cheerio pass in this change:** `scripts/sri.mjs:62-126` and `scripts/csp.mjs:142-256` remain separate stages with their own post-write disk re-read audit (`scripts/csp.mjs:218-255`). - **Production changes from Spikes 5A, 5B, or 5C:** Astro-native CSP adoption, bulk `node:test` → `vitest` migration, and `/assets/theme.css` bundling are scoped strictly as measurement/feasibility spikes that produce evidence reports; any follow-on behavior change requires its own OpenSpec delta after spike acceptance.
